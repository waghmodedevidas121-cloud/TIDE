Prototype Technical Design

Validates one question: does terrain-constrained routing create meaningful territory-control decisions? Everything in this document exists to make that question answerable in a single playtest.

No code written yet TypeScriptPhaser 3 · renderer only WebGL48 × 48 grid1 human + 1 bot

00 What this prototype must prove

The single question

Does a static bathymetric map — where shallow water is slow and sand is impassable — create a routing decision that a player actually thinks about?

It succeeds if, within 30 seconds of spawning, a player can point at two routes and say which is safer.

It fails if players route as if the map were blank — hugging open water regardless of terrain, or ignoring deep channels because they never notice them.

Everything below is designed to make one of those two outcomes unambiguous to observe.

01 Architecture decision — engine-independent simulation

This contradicts the brief's "Phaser 3" instruction, deliberately

The Phase 0 review concluded the simulation core must not depend on the engine. The brief specified Phaser 3. Both are satisfiable — but only if Phaser is used strictly as a renderer.

Paper.io's architecture rests on one property: src/core/ is imported byte-for-byte by the server, the browser, and every bot, so there is exactly one simulation. That is what makes its lockstep netcode cheap. If the simulation is written inside Phaser scenes, that property is destroyed and reconstructing it later in Beta means rewriting the entire game.

The rule for Phase 1

The simulation is a plain TypeScript module. It imports nothing. Not Phaser, not the DOM, not Math.random. It exposes state and a step() function. Phaser reads that state each frame and draws it.

What this buys us in the prototype itself: the bot runs the exact same simulation code as the player, in the same process, with no networking at all. That is not a Phase 4 convenience — it is the cheapest possible way to make the bot credible, which is one of our success conditions.

02 Coordinate system and movement

Ported unchanged from the Paper.io analysis, because it is the reason that game feels crisp.

  • Continuous position in world units, 1 cell = 1 unit. Not grid-locked.
  • Four directions only. No diagonals, no analogue steering. One control.
  • Turns are only applied when the boat sits exactly on a cell line. Input is latched into pendingHeading and consumed at the next boundary.
  • Steps clamp to the next cell line, so a slow cell can never overshoot into the next one. This is the one thing Paper.io's clone does not handle (it assumes constant speed) and we must.
  • Reversals are rejected client-side, as in the clone — you cannot turn into your own tail.

Speed by depth — the core variable under test

CellPassableSpeedRationale
DEEPyes1.00 × (4.0 cells/s)The highway. Fast, exposed, contested.
SHALLOWyes0.50 × (2.0 cells/s)The margin. Twice the exposure for the same trip. Safe by default.
SANDno—Impassable. Also a capture boundary.
Why this is the only new variable

Bathymetry reduces to exactly two changes over stock Paper.io: a speed multiplier keyed on a terrain layer, and sand added to the set of things that stop a flood fill. If the concept works, these two changes are sufficient. If it fails, no amount of additional terrain complexity will rescue it — which is what makes the prototype cheap and the verdict trustworthy.

03 Territory ownership

Deliberately not the clone's model. The clone stores a Player object reference per cell; we store a flat typed array of IDs.

Storage

Uint8Array(48×48). Index 0 = neutral, 1 = human, 2 = bot. 2,304 bytes. Serialisable in one line when netcode arrives.

Dirty tracking

A Set<number> of changed indices, drained each frame by the renderer. Only changed cells are redrawn — this is what keeps a full-map WebGL view cheap.

Score is maintained incrementally: +1 / −1 on every ownership change, exactly as Paper.io's client did. Score is territory cells ÷ claimable cells, displayed as a percentage to two decimals — sand is excluded from the denominator, so 100% is genuinely reachable.

05 Capture algorithm — where the mechanic lives

Identical to Paper.io's proven algorithm with one substitution. Fires the moment the boat's centre enters a cell it owns.

fillTail():   BFS across every cell the trail touches
                mark visited
                claim the trail cell itself
                flood outward from all 4 neighbours

floodFill():  expand until blocked by:
                SAND          <-- THE ONLY CHANGE. Sand behaves exactly
                out of bounds       like the map edge.
                already visited
                own trail
                own territory
              if the flood escaped -> that region is NOT claimed
              otherwise -> write the whole region to the player
Why treating sand as "map edge" is the right move

Paper.io's capture works because the flood fill leaks to the world border when a loop is open. Sand leaking the flood behaves identically, so enclosure logic needs no new code path at all — the flood simply never reaches the cells behind a sand bank. It also gives the correct emergent behaviour for free: a sand bank in the middle of your loop is an island, and you cannot claim through it.

The learning moment this produces: a player who tries to enclose the central lagoon will fail repeatedly, because the lagoon is only reachable through four narrow keyholes and a loop must go around the sand to close on itself. Getting it right is a genuine spatial insight — the exact thing we want to observe in playtest.

06 Collision, death, respawn

EventResultNote
Enter SANDBlocked — movement stops at the cell lineDeliberate. Four death causes was too many for one playtest; blocking keeps players alive longer so they make more routing decisions. "Sand kills" is the aggressive variant to test in Alpha.
Enter own trailDeathUnchanged from Paper.io. Self-inflicted and visible.
Enter map borderDeathBorder is drawn as a hard frame; with the whole map visible this should be near-zero.
Collide with larger boat outside territoryDeathPaper.io's area(p) tiebreak: the player less committed to the current cell loses. Deterministic and sub-frame-fair.
Collide with smaller boat while on own landThey dieKeep Paper.io's safe-zone rule. It is the best rule in that game and it is what makes a large territory feel defensible.
On deathAll owned cells → neutral. Respawn after 1.0s at a spawn point far from the other player.Territory erasure is Paper.io's verified behaviour and is intentional here: it makes the map a renewable resource and creates the comeback dynamic the genre depends on.
Two deliberate deviations from "just port Paper.io"

(a) Sand blocks instead of kills. Reasoned above — it preserves session length for measurement.
(b) Death erases territory. This is Paper.io's actual behaviour (core/index.js:94), not an invention. It was mis-stated in our own Phase 0 as "you keep your land." The corrected behaviour is the more interesting one and it is retained.

07 Bot design

No new architecture. The bot extends Paper.io's proven three-state policy with terrain awareness — the minimum change needed for it to look credible rather than broken.

StateTriggerBehaviour
EXPANDon own land, share < 12%Execute a pre-generated rectangle (side lengths 2–6 cells), but abort the turn if the next cell is sand. Recomputes the remaining path from the current cell if the path is broken.
HUNTon own landPaper.io's raycast, extended with a sand distance term at a strong negative weight. Enemy tails keep their large positive weight.
RETURNoutsideRaycast homing on own territory, plus strong aversion to sand and to own trail.
The bot must be beatable-looking

A bot that respects terrain perfectly will feel like a wall. A bot that ignores it will look broken. The target is visibly fallible: committed to a plan it abandons when sand blocks it, and occasionally cut off by a player who read the map better. Bot decision rate stays at Paper.io's proven 6-frame cadence (10 Hz) — faster looks robotic.

08 Rendering and the legibility spec

Legibility was the #1 risk identified in Phase 0

Terrain is a second visual language layered on top of territory and trails. It is also the thing the prototype exists to test. If a player cannot read the terrain in 30 seconds, the concept is dead regardless of how good the routing decisions are. The visual priority order below is a hard constraint, not a preference.

Visual priority — highest salience first

RankElementTreatmentWhy
1TrailFully opaque, saturated player hue, brightest thing on screenYour trail is what kills you. It must dominate.
2BoatWhite core + player-hue ring, drawn above everythingLocating yourself must be instant.
3Territory boundaryBright 1-cell outline on owned cells bordering non-owned cellsShows shape and defensibility at a glance.
4Territory fillPlayer hue at ~45% alpha over terrainOwnership readable without hiding the terrain beneath it.
5TerrainStatic. Rendered once to a texture.Background context, never competing for attention.

Palette — chosen for contrast against territory colour, not for prettiness

ElementColourReason
DEEP#0d2f4a dark navyDarkest value on screen. "Fast" reads as "open".
SHALLOW#2e9fd4 mid cyanTwo full steps lighter. The speed penalty must be visible before it is felt.
SAND#d9c48a warm tanOnly warm hue on the map. Instantly reads as "not water". Hue contrast beats value contrast here.
Territory fillPlayer hue @ 45%Alpha blend keeps terrain legible underneath.
Territory edgePlayer hue, fullShape at a glance.

Sand is the only warm colour on screen. That single decision is what makes the map readable in under a second, before any UI explains anything.

Camera — fixed, full map, no scroll, no zoom

This is derived directly from the success condition

To identify a route a player must see more than one route. On a scrolled camera they cannot. Therefore the whole map is always visible.

Benefits beyond the test: both players are always in frame (the entire point of .io), sand can never be entered accidentally by an off-screen player, and it is the cheapest possible renderer — 48×48 cells scaled to fit, one static texture plus dirty-cell overlays. Downside accepted: no sense of scale or pursuit. Noted for Alpha.

09 Determinism notes — for Phase 4, free now

Because the core is engine-independent, it costs nothing to keep it netcode-ready:

  • No Math.random() inside the core. Bot randomness uses a seeded generator stored in the core and passed in.
  • No accumulated float state. Position is integer cell + integer sub-step offset, not a drifting float. This removes an entire class of future desync bugs.
  • Fixed 10 Hz simulation tick, decoupled from the 60 Hz render. All rates expressed per tick, never per frame — the single most important lesson from the source analysis.
  • Terrain is immutable after load, so it never needs to be transmitted per frame. One message, once.

10 Explicit non-goals for Phase 1

Not built

  • Backend, netcode, accounts, matchmaking
  • Multiplayer beyond one bot
  • Round timer, match end, results screen
  • Progression, cosmetics, currency
  • Monetisation of any kind
  • Audio
  • Any external art asset
  • Zoom, camera follow, particle effects
  • Terrain animation or water shader

Deliberate deferrals

  • Procedural graphics only. No image files, no sprite sheets, no fonts beyond system. Terrain and boats are drawn primitives.
  • Sand as a killer. Deferred to Alpha pending playtest.
  • Mobile polish. Touch input is included and the full-map camera helps enormously, but performance tuning is deferred.
  • Second and third bot archetypes. One bot, per brief.
