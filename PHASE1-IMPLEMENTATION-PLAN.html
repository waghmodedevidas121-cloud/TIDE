Implementation Plan

Nine milestones, each independently verifiable, each on its own branch, each ending in a thing you can play. The last milestone is not a build — it is a decision.

Estimated 8–11 working days 9 milestones GitHub-first Ends in a PASS / FAIL gate

00 The sequencing principle

Why the order is what it is

Three rules decide every sequence below:

  1. Nothing is unplayable for longer than one milestone. After M3 the player can move and capture. We would rather have a crude loop on day three than a perfect loop on day eleven.
  2. Terrain comes last, not first. The enclosure loop is ported from a proven algorithm. We ship it working before adding a single sand cell, so that if the concept fails we know it was the terrain and not the capture code.
  3. Bot before polish. A credible opponent is a success condition. It is also the cheapest possible source of load and corner-case discovery.

01 Milestones

Milestone 1 Grid, map loader, static terrain render
feature/map-loader
Build
Parse the 48×48 map file into a terrain array. Add a isPassable and speedAt query. Render the whole map once into a Phaser texture and display it. Phaser shell, camera fixed on the full map.
Verify
Map renders. Cell (24,18) is deep. Cell (20,20) is sand. speedAt returns 0.5 on any shallow cell.
Exit criteriaThe map is on screen and correct at a glance. Someone who has not seen the design doc can name the tan shapes as "land".
Milestone 2 Boat movement and buffered input
feature/boat-movement
Build
Continuous position, integer cell + sub-step offset. Four buffered headings. Turn consumed only on a cell line. Step clamped to the next boundary so slow cells cannot overshoot. Keys, then swipe.
Verify
Turns feel crisp. The boat never skips a cell. Reversal attempts are ignored. Touch swipe works.
Exit criteriaMovement feels identical to Paper.io. This is the one thing that must not regress — if it feels wrong here it will feel wrong everywhere.
Milestone 3 — first playable Trail and area capture
feature/trail-capture
Build
RLE trail plus sparse hit-grid. fillTail + floodFill with no terrain handling yet — everything passable, so this is stock Paper.io. Territory as Uint8Array. Dirty-cell set.
Verify
Leave territory, loop, return, bank the area. Hitting your own trail does nothing yet.
Exit criteriaA stranger captures territory within 60 seconds of being handed the build, with no instruction. This is the Paper.io success condition, reproduced as our own baseline before any concept work begins.
Milestone 4 Death, respawn, score
feature/death-respawn
Build
Own-tail death. Border death. Body collision with the area(p) tiebreak and the safe-zone rule. Death clears all owned cells to neutral. 1.0s respawn at the far spawn point. Score = cells ÷ claimable, two decimals.
Verify
All four collision outcomes reachable and correct. Territory is erased on death. Score decrements correctly.
Exit criteriaEvery death cause is legible and attributable. The player can say why they died, every time.
Milestone 5 Rendering pass and HUD
feature/render-hud
Build
Territory fill at 45% alpha plus boundary outline, dirty-cell redraw. Trails opaque. Boats with white core. HUD: own %, opponent %, kills, both boat colours. Death flash.
Verify
Visual priority order holds: trail dominates, boat locates instantly, territory is readable without hiding terrain.
Exit criteriaSimultaneously readable: both boats, both territories, both trails, and three terrain types, at 1920px and at 390px.
Milestone 6 — THE CONCEPT Bathymetry: speed and sand
feature/bathymetry
Build
Two changes only. (a) Speed multiplier from the terrain layer — deep 1.0×, shallow 0.5×. (b) Sand added to the flood-fill boundary set and to the movement collision set. Nothing else changes.
Verify
Boat is visibly slower in shallows. Cannot enter sand. A loop cannot enclose across sand. The lagoon can be enclosed by driving a perimeter around the mainland — test this explicitly.
Exit criteriaSpeed difference is immediately perceptible without being told. The lagoon perimeter loop is confirmed possible. Total new code is under ~150 lines.
Milestone 7 The bot
feature/bot
Build
Three-state policy — expand, hunt, return — running the same core in the same process. Sand term in the raycast at strong negative weight. Rectangle path aborts and recomputes on sand. Seeded RNG, not Math.random.
Verify
Bot captures land. Bot never drives into sand. Bot visibly abandons a blocked plan. Bot occasionally dies to the player.
Exit criteriaBot is beatable-looking — visibly fallible, and its mistakes are ones the player could have predicted. A competent player beats it by reading the map.
Milestone 8 Touch, telemetry, tuning
feature/telemetry-mobile
Build
Touch controls sampled at the frame boundary. Five counters. All tuning knobs live-editable. DPR capped at 2.
Verify
Playable one-handed on a phone. Counters visible. Speed ratio sweepable without a rebuild.
Exit criteriaA full test session can be run on a phone with no visible stutter and no mis-taps.
Milestone 9 The gate — playtest and decide
docs/phase1-verdict
Do
Run the protocol below. Collect the numbers. Write a verdict document. No new features.
Exit criteriaA written PASS or FAIL with evidence, and a decision on whether TIDE continues.

02 Telemetry — five counters, no more

CounterWhat it measuresWhy it exists
timeToFirstCaptureSeconds from spawn to first banked loopBaseline comprehension check.
trailCellsByTypeTrail cells laid in deep vs shallowThe primary terrain metric. Is the speed rule biting?
sandBlockedTimes movement was stopped by sandProof the player is testing terrain rather than avoiding it by luck.
lagoonAttemptsLoops that entered a keyholeWhether the prize and the chokepoint are being noticed at all.
deathsByCauseTail / border / body / sandConfirms deaths stay fair and legible.

These are research instrumentation, printed to the browser console. They are not a game feature, not networked, not persisted, and must be removable in a single commit after the gate. Five counters is the ceiling — anything more and we start optimising for the metric instead of for the answer.

03 Playtest protocol

Three sessions, one tester, 5 minutes each

One internal tester is enough for a legibility test. It is not enough for a fun test — that is Alpha's job with real players.

WhenTester is asked to doWhat we are looking for
30sStop. Point at the safest route from where you are toward the middle of the map, and say why.THE KILL-TEST. Does they point at deep water, shallow water, or "no idea"? Do they mention the tan shapes at all?
90sPlay.Does the territory form channel-following ribbons, or open-water blobs? Ribbons = pass.
3mKeep playing.Has anyone entered a keyhole? Has anyone tried to enclose the lagoon and hit the wall?
5mStop. Answer three questions.See below.

The three questions

  1. "Did the map shape change where you went, or did you just ignore it?"
  2. "Was there a moment you chose a longer route on purpose? What made you do that?"
  3. "What was the map's dark shape? Describe it." — the silhouette test. If they cannot name it in one breath, visual identity has failed.

Question 3 is the cheapest possible proxy for the visual-identity concern from Phase 0: if a player cannot describe the map's shape unprompted, it will not be identifiable in a thumbnail either.

04 The gate — explicit thresholds

Decided in advance, so it cannot be rationalised later

This is the same discipline used to kill the tide. Thresholds are set before the prototype exists, while it is still cheap to be honest about the result.

MetricPASSFAIL
Route identification at 30sNames deep or shallow water as the deciding factorPoints at open water, or cannot say
Territory shapeRibbons following channelsBlobs in open water
Deep-vs-shallow trail splitBoth > 20%Shallow < 10% — the speed rule is inert
Silhouette recall (Q3)Describes a shape in one breath"It's just water"
Keyhole noticed by 3 minYes, or attempted the lagoonNot required to pass
Deaths attributableTester names the cause every timeAny "I don't know what happened"
Two outcomes that are not passes, whatever the numbers say
  1. The map reads as decorative. The tester describes it accurately but says it did not matter. That means the terrain is legible but strategically irrelevant — and legibility was never the goal.
  2. The tester plays the lagoon puzzle and nothing else. Finding one hard puzzle and grinding it is not evidence that terrain creates decisions. Watch for tunnel vision in the telemetry.
If it FAILS

Pivot to Forge. Terrain-constrained routing does not produce routing decisions → the map is decoration → remove the terrain concept entirely and build Forge (cooling territory, a player-paid holding cost), which attacks the same retention problem through the economy instead of the layout. That is the fallback already identified in the concept ranking.

05 Git workflow

main        stable only, branch-protected, never pushed to directly
development integration branch
feature/*   one branch per milestone

  git switch development && git pull
  git switch -c feature/boat-movement
  ... work, commit per logical step ...
  git push -u origin feature/boat-movement
  open PR -> CI -> review -> merge into development
  ... playable build tagged on development ...
  # development -> main only when a milestone gate passes

Commit convention

feat: add buffered turn handling at cell boundaries
feat: implement flood-fill capture with sand boundary
feat: extend bot raycast with terrain term
fix: clamp sub-step movement at cell lines to avoid overshoot
fix: lagoon perimeter loop captured no cells
refactor: extract passability query from terrain array
perf: redraw only dirty territory cells
chore: remove post-gate telemetry counters

Rejected: update, changes, fixes, work, wip.

CI on every PR: typecheck, build, and a headless simulation smoke test — 2,000 ticks of the core with scripted input, asserting no NaN and no out-of-bounds write. The core is engine-independent precisely so this test is cheap to write, and it is the earliest warning that determinism has drifted.

RiskSeverityResponse

Bot is either trivial or infuriatingHIGHThree-state policy already has a known weakness. Tune the sand weight and the expand threshold only — no new behaviours in Phase 1.

Determinism drifts, breaking the smoke testLOWCaught by CI at the moment it happens. This is the whole point of the engine-independent rule.

The most valuable thing this budget buys

It buys a disproven or proven answer in eight days to a question we cannot currently answer by argument. Every hour spent on a tenth concept is an hour not spent finding out whether the first one works. That is the entire argument for stopping design and building this.
